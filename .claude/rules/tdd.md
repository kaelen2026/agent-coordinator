# TDD 规则

`testing.md` 定义"必须测什么"；本文件定义"以什么顺序开发"。新业务逻辑默认走 TDD。

## 红-绿-重构循环（每个行为一轮）

1. **红**：先写一个描述目标行为的测试，运行并**确认它失败**、且失败原因正确（是断言失败，不是编译错误或 setup 错误）。没见过红的测试不可信。
2. **绿**：写最少量的实现代码让测试通过，抵制顺手实现"以后会用到"的部分。
3. **重构**：测试保持绿的前提下消除重复、改善命名；每次重构后立刻跑测试。

一轮只驱动一个行为，循环要小：单轮超过 ~15 分钟说明步子太大，拆小。

## 适用范围

**必须 TDD**：
- service 层新业务规则（状态转移、权限判定、计算逻辑）
- bug 修复：先写复现测试（红），确认复现了再修（绿）——这条无例外
- 涉及幂等、重试、并发的逻辑

**可不 TDD（实现后补测试即可，底线仍是 `testing.md`）**：
- 纯粹的胶水/配置代码（路由注册、依赖装配）
- 探索性 spike：允许先裸写摸清方案，但 spike 代码必须丢弃，正式实现从测试开始重写
- 数据库迁移脚本（由集成测试整体覆盖）

## 切片方式：tracer bullet 纵向切

- 按"一条走通的行为路径"切片（API 入口 → service → 存储），不按层横向切。每个切片完成后系统端到端可运行。
- 第一颗 tracer bullet 打最主干的正向路径，之后每轮循环补一个边界或异常路径。
- 测试驱动的是**对外可观察行为**（输入 → 输出/副作用），不驱动内部实现细节——不给私有函数单独写测试，否则重构时测试成为阻力。

## 纪律

- 禁止"实现写完了再补一批测试然后声称是 TDD"——提交历史（或工作过程描述）应能看出测试先行。
- 测试失败时禁止：改断言迁就实现、加 skip、扩大 mock 范围让它绿。先判断是测试错了还是代码错了。
- 每轮循环结束跑全量相关测试，不只跑当前这个。
- backend-engineer 交付时需说明哪些行为是测试驱动的；reviewer 抽查测试是否真的能约束实现（删掉实现关键行，测试应变红）。
