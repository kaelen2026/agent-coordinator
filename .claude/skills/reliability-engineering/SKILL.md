# 可靠性工程 SOP

**输入**：一个服务或一次涉及外部依赖的改动。**输出**：每个依赖有防御与降级、服务可被观测、变更可回退。

## 步骤 1：给每个出站依赖配防御（按序叠加，前三项是底线）

1. **超时**：连接 + 读写分开设——没有超时的调用等于把线程池抵押给对方；
2. **重试预算**：只重试幂等操作，指数退避 + 抖动，限次数限总时长；
3. **限流**：入口按租户/IP 令牌桶保护自己，出口限流保护下游；
4. **熔断**：错误率超阈值快速失败，半开放探测流量；
5. **舱壁**：不同依赖独立连接池/信号量，一个卡死不拖垮全部。

- ✅ 检查点：逐个依赖过一遍 1-3 项，缺一项都不算完成。

## 步骤 2：为每个非核心依赖写降级答案

逐个依赖回答："它挂了，本服务还能提供什么？"答案写进代码：返回缓存、默认值、跳过该步骤，或明确拒绝该子功能。

- ✅ 检查点：每条降级路径有测试（模拟依赖故障触发），没测试的降级等于没有。

## 步骤 3：配置生命周期

- 健康检查分两种：liveness 只查自身进程；readiness 查关键依赖连通。依赖抖动只摘 readiness，不重启进程。
- 启动顺序：建好依赖连接、通过迁移检查后再上报 ready。
- 优雅停机：SIGTERM → 摘 readiness → 停接新请求 → 排空在途请求与任务 → 关连接 → 退出，全程小于编排系统宽限期。
- ✅ 检查点：kill 进程演练一次，确认无请求丢失。

## 步骤 4：接入可观测性三件套（分工不互替）

- **结构化日志**（JSON）：每条带 `request_id`/`trace_id`；每个请求记一条汇总日志（方法、路径、状态码、耗时）；ERROR 只留给需要人处理的事。
- **指标**：暴露 RED（请求率、错误率、P50/P95/P99 时延）+ 资源（连接池、队列深度、任务滞后）——队列深度与任务 age 是异步系统最重要的先行指标。
- **追踪**：trace_id 贯穿入站请求 → 出站调用 → 队列消息（写进消息头）。

## 步骤 5：配告警

- 针对症状（用户可感知的错误率/延迟/积压）告警，不针对原因（CPU 高不一定是问题）。
- 每条告警可行动：附 runbook 或一句"先看什么"；会自愈的波动进 dashboard 不进告警。

## 步骤 6：变更安全

- 高风险行为加 feature flag，出问题先关开关再排查。
- 新功能灰度：小流量 → 观察 RED 指标 → 放量；观察窗口内指标回归即回退。

## 完成检查

- [ ] 每个出站调用有超时/重试预算/失败路径
- [ ] 每个非核心依赖有降级答案且有测试
- [ ] 核心接口有 RED 指标与可行动告警
- [ ] 优雅停机演练通过

## 最佳实践（推荐，非强制；偏离时说明理由）

- 先定 SLO 再谈可靠性投入：没有目标（如"月可用 99.9%、P95 < 300ms"）就无法回答"够不够可靠"，也无法用错误预算决定该加固还是该发功能。
- 超时值从下游实测 P99 推导（如 P99 × 1.5），不拍脑袋写 30s——过长的超时在故障时把线程池耗干。
- 破坏性运维操作（批量删除、回填、配置大改）先支持 dry-run 输出影响面，执行留审计日志。
- 容量靠负载测试找拐点而不是猜：知道系统在多少 QPS 开始劣化，日常水位保持在拐点的 50-70%。
- 故障演练从测试环境开始、小剂量常态化（杀 pod、断依赖、注入延迟），比年度大演习更能暴露真实弱点。
- 每个告警配 runbook 与告警同 PR 提交；响应过一次事故后 24h 内把"当时怎么查的"沉淀回 runbook。
- 事故复盘对事不对人（blameless），产出是系统性修复项而不是"下次小心"。
