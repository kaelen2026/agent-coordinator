# 任务队列 SOP

**前提认知**：投递语义是至少一次（at-least-once），重复投递必然发生——所以处理器幂等不是优化，是步骤 3 的强制项。

**输入**：一个需要异步执行的行为。**输出**：幂等的任务处理链路 + 重试/死信机制 + 针对性测试。

## 步骤 1：定义任务模型

任务记录（无论 Redis/RabbitMQ/DB 表实现）至少包含：

```
id, type, payload(JSON), status(pending|running|done|failed|dead),
attempts, max_attempts, run_at, locked_by, locked_at, last_error
```

- payload 只放 ID 和必要参数，处理时按 ID 重查最新状态，不放对象快照。
- 状态转移画成显式状态机，非法转移直接拒绝。
- ✅ 检查点：每个状态都有进入和退出路径，没有进得去出不来的状态。

## 步骤 2：入队与业务事务的边界

业务数据和任务记录必须同事务落库——用 **transactional outbox**：本地事务写业务表 + 任务表，分发器扫描投递。禁止"先发消息再提交事务"或反之。

定时任务：cron 触发 + 分布式锁（DB advisory lock 即可）保证单实例执行；写明错过调度的策略（跳过 or 补跑）。

## 步骤 3：实现幂等处理器

按优先级选幂等手段：

1. 数据库唯一键吞掉重复插入；
2. 状态机条件更新（`UPDATE ... WHERE status='pending'`，影响行数为 0 说明已处理）；
3. 显式去重表记录已处理 job_id。

- ✅ 检查点：写一个"同一消息投递两次"的测试，两次结果与一次相同。

## 步骤 4：错误分类与重试

处理器里区分两类错误并分别处理：

- **可重试**（网络超时、依赖 5xx、死锁）→ 指数退避 + 抖动重排：`min(base * 2^attempts + jitter, cap)`；
- **不可重试**（参数非法、业务规则拒绝）→ 直接标 failed，不浪费重试。

超过 `max_attempts` 进 dead（死信）：保留完整 payload 与 last_error，触发告警，且支持人工一键重放。

## 步骤 5：保证 worker 正确性

- 取任务原子化：`FOR UPDATE SKIP LOCKED` 或队列原语，两个 worker 不会抢到同一任务。
- 租约回收：worker 崩溃后靠 `locked_at` 超时 + reaper（或 broker 可见性超时）把 running 任务放回，不永久卡死。
- 单任务硬超时，防止坏任务占死 worker。
- 优雅停机：SIGTERM 后停取新任务、跑完手头再退，总时长小于部署系统 kill 宽限期。
- ✅ 检查点：kill -9 一个正在处理的 worker，任务最终仍被完成。

## 步骤 6：测试

必测四项：重复投递幂等（步骤 3）、可重试错误的退避行为、不可重试错误直达 failed、worker 崩溃回收（步骤 5）。方法见 `backend-testing` skill。

## 完成检查

- [ ] outbox 保证任务与业务数据同事务
- [ ] 幂等测试（重复投递）通过
- [ ] 错误分类明确，死信有告警和重放路径
- [ ] worker 崩溃恢复验证过

## 最佳实践（推荐，非强制；偏离时说明理由）

- 任务粒度宜小且单一职责：长流程拆成链式任务（每步完成后入队下一步）或带 checkpoint 可续跑，而不是一个跑半小时的巨任务。
- 优先级用独立队列 + 独立 worker 池实现，不用同队列的优先级字段——后者在积压时低优任务会饿死且难观测。
- 大批量定时入队加抖动错峰（如每日结算任务把 run_at 打散到几分钟内），避免整点惊群。
- payload 带 `version` 字段：滚动部署期间新旧 worker 并存，处理器按版本兼容。
- 任务处理器内不再同步调用慢的外部接口——把那一步拆成下一个任务，否则一个慢依赖拖垮整个队列吞吐。
- 监控盯先行指标：队列深度、最老任务的 age、死信增速；这三个恶化时用户还没感知，是最好的介入时机。
- 给死信重放做成一条命令/按钮，并在重放前允许修 payload——排障时的效率差别巨大。
