# API 设计 SOP

**输入**：一个切片的 DoD。**输出**：冻结的 API 契约 + 符合契约的实现与契约测试。

## 步骤 1：资源建模

从 DoD 里找出名词（task、run、worker），确定每个名词是资源还是子资源。

- URL 用名词复数：`/tasks`、`/tasks/{id}/runs`；实在无法资源化的动作用 `POST /tasks/{id}:cancel`。
- ✅ 检查点：每个 DoD 行为都能映射到"方法 + URL"，没有 `/doSomething` 式动词接口。

## 步骤 2：定义方法语义与状态码

每个 endpoint 确定：方法、认证要求、幂等性、成功与失败状态码。

| 场景 | 状态码 |
|---|---|
| 创建成功 | 201 + `Location`；异步受理 202 + 可轮询资源 |
| 参数校验失败 | 400 |
| 未认证 / 无权限 | 401 / 403（区分开） |
| 不存在或无权查看 | 404（不向无权者暴露存在性） |
| 状态冲突（重复创建、乐观锁失败） | 409 |
| 限流 | 429 + `Retry-After` |
| 服务端错误 | 500（不泄露内部细节） |

方法语义：GET 无副作用；PUT 全量替换且幂等；PATCH 部分更新；DELETE 幂等且行为全项目一致。

## 步骤 3：定义 schema 与错误格式

写出每个 endpoint 的请求/响应 schema。错误响应全局统一：

```json
{ "error": { "code": "TASK_NOT_FOUND", "message": "人类可读描述", "details": [] } }
```

- `code` 是稳定枚举，客户端逻辑只依赖 code。
- 列表接口一律分页：游标分页优先（`?cursor=...&limit=50`），页大小设上限（如 100），响应带 `next_cursor`。
- 创建类 POST 声明支持 `Idempotency-Key`，同 key 重放返回首次结果。
- ✅ 检查点：每个字段有类型与约束；每个业务失败场景有对应 error code。

## 步骤 4：契约评审与冻结

把契约（endpoint 清单 + schema + 错误码表）交 coordinator 确认；跨端任务由 coordinator 广播给各端。确认后契约冻结——中途要改必须回到本步骤重新走。

## 步骤 5：实现与契约测试

按契约实现；每个 endpoint 写契约测试：正向路径断言响应 schema 与状态码，异常路径逐个覆盖步骤 2 表中声明的失败场景。

破坏性变更（删字段、改语义、改状态码）不允许直接改：进 `/v2/` 或开新字段过渡。

## 完成检查

- [ ] 契约文档已被 coordinator 确认且实现与之一致
- [ ] 每个 endpoint 有认证声明与限流
- [ ] 错误 code 稳定、格式统一；列表有分页上限
- [ ] 契约测试覆盖每个声明的状态码

## 最佳实践（推荐，非强制；偏离时说明理由）

- 契约落盘为 OpenAPI 文档，且从 schema 代码生成（或反向校验），防止文档与实现漂移。
- 字段命名全项目统一（如 JSON 一律 snake_case）；时间字段一律 ISO 8601 UTC、以 `_at` 结尾；金额字段名带单位（`amount_cents`）。
- 响应不包 `{code, data}` 双层壳——HTTP 状态码已表达成败，多壳只会让客户端判断两次。
- 批量接口如果允许部分成功，逐项返回结果（每项带 index + 成败 + 错误码），不做隐式的"全有全无"。
- 对外 webhook：带事件 `id`（消费方去重）+ 签名（防伪造）+ 失败重试；文档写明重试策略。
- 枚举字段文档写明"未来可能新增值"，逼客户端写兜底分支。
- 预估会超 1s 的操作从第一版就设计成异步（202 + 状态资源），事后从同步改异步是破坏性变更。
