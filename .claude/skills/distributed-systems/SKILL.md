# 分布式系统 SOP

**前提认知**（所有步骤由此推出）：① 调用会超时，超时后你不知道对方执行了没有；② 没有全局时钟，跨机时间戳不能定序；③ exactly-once 不存在，只有 at-least-once + 幂等消费。

**输入**：一个涉及跨服务/跨进程的行为。**输出**：幂等、有超时预算、一致性档位明确的实现。

## 步骤 1：标出所有跨界写操作，逐个加幂等键

列出该行为里每一次"跨过进程边界的写"（调下游 API、发消息、写共享存储）。每个写操作：

- 调用方生成幂等键（UUID）随请求传递；
- 接收方把幂等键与结果一起持久化，重放请求返回首次结果而非报错；
- 幂等靠唯一约束或原子条件更新落地——"先检查再执行"有竞态，不算。
- ✅ 检查点：每个跨界写都能回答"这个请求重放一次会怎样"。

## 步骤 2：配置超时与重试预算

对每个出站调用：

- 连接超时与读写超时分开设；上游总超时 < 下游各步超时之和，否则重试打在已死的请求上。
- 只重试幂等操作；重试用指数退避 + 抖动，总预算有限（如 3 次或累计 2s）——重试是放大器，无预算的重试把抖动放大成雪崩。
- ✅ 检查点：没有任何一个网络调用缺超时。

## 步骤 3：选一致性档位（从便宜到贵，够用就停）

1. **单库事务**：能塞进一个数据库事务的就塞进去；
2. **Transactional outbox + 事件**：跨服务最终一致的默认方案（见 `job-queue` skill 步骤 2）；
3. **Saga（补偿）**：多步跨服务流程——先画状态机，给每个失败点写补偿操作，接受中间状态可见；
4. **两阶段提交**：几乎永远不选，想选时先质疑服务边界划错了。

- ✅ 检查点：能说出"为什么档位 N-1 不够用"，说不出就降档。

## 步骤 4：锁需求质疑与实现

先尝试无锁替代：唯一约束、原子更新、队列串行化通常更可靠。确实需要锁时：

- 带 TTL 的租约锁（Redis `SET NX PX` / PG advisory lock），持锁方定期续租；
- 锁内操作要么短于 TTL，要么用 fencing token 防旧持有者复活写脏数据；
- 定时任务防多实例并发用 DB advisory lock，简单可靠。

## 步骤 5：事件设计（如果方案含事件）

- 事件载荷带 `event_id`（去重）、`occurred_at`、聚合根 `version`（定序）。
- 消费者不假设按序到达；需要顺序时按聚合根分区（同一 task 的事件单线程处理）。
- schema 演进只加字段不删改，消费者容忍未知字段。

## 完成检查

- [ ] 每个跨界写有幂等键且重放行为已测试
- [ ] 每个出站调用有超时，重试有预算
- [ ] 一致性档位是够用的最便宜档
- [ ] 锁有 TTL 与续租，或已用无锁方案替代

## 最佳实践（推荐，非强制；偏离时说明理由）

- 最好的分布式问题是不产生它：能放进同一个服务/同一个库的逻辑不要跨界，拆服务的动机应是团队与部署边界，不是"看起来更架构"。
- 读多写少的跨服务数据用缓存 + TTL 容忍有界陈旧，比实时跨服务查询便宜一个量级；先和产品确认"多旧可接受"。
- 测量耗时用单调时钟（monotonic clock），不用墙钟——NTP 校时会让墙钟差值出现负数。
- 滚动部署期间新旧版本并存是常态：事件/消息的生产者先兼容双版本再切换，消费者永远容忍旧格式，保留一个部署周期的兼容窗口。
- 背压优先于无界缓冲：下游处理不过来时让上游感知（限流、拒绝、队列上限告警），无界队列只是把 OOM 延后。
- 跨服务调用链控制在 2-3 跳内；更深的链路考虑改编排（一个协调者发任务）代替层层同步透传。
- 每个降级/补偿路径都要有触发演练的办法，长期不触发的路径大概率已经坏了。
