# 数据库设计 SOP

**输入**：切片的数据需求与查询场景。**输出**：schema + 索引 + 可安全上线的迁移 + 集成测试。

**本仓库落地（PostgreSQL 17 + Drizzle）**：

- ORM 用 **Drizzle**，迁移用 **drizzle-kit**：schema 以 TypeScript 定义（modular monolith——每个模块的表定义放该模块内，drizzle 配置汇总），`drizzle-kit generate` 产出 SQL 迁移文件入库走 review，禁止手改已生成的历史迁移。
- 生成的迁移 SQL 必须人工过一遍本 SOP 步骤 5 的不停机检查（drizzle-kit 不懂锁表风险）。
- 本地库：`pnpm infra:up`（见 CLAUDE.md 本地基建）；首个用到数据库的切片再引入 drizzle 依赖（简单优先，不预装）。

## 步骤 1：列出查询场景，再建模

先写下这个切片的所有读写路径（"按 tenant + status 查任务列表，按时间排序"），再设计表——表结构服务查询，不反过来。

- ✅ 检查点：每张新表都有至少一个明确的查询场景；查不到的字段不建。

## 步骤 2：写 schema

每张表基线：`id`（bigint 自增或 UUIDv7，全项目统一）、`created_at`、`updated_at`（UTC，数据库层默认值）。

- 约束进数据库：NOT NULL、UNIQUE、FK、CHECK 能加就加——应用有 bug 时数据库是最后防线。
- 枚举用短字符串 + CHECK（`status IN ('pending','running','done','failed')`）。
- 金额用整数最小单位或 DECIMAL；会被 WHERE 的字段必须是独立列，不埋 JSON。
- 需要软删除的实体用 `deleted_at`，同时保证所有查询默认过滤，UNIQUE 索引含 `deleted_at`。
- ✅ 检查点：唯一性需求全部落成 UNIQUE 索引，没有"应用层先查再插"。

## 步骤 3：设计索引

对步骤 1 的每个查询路径设计索引，复合索引按最左前缀排列：`(tenant_id, status, created_at)` 服务"按租户按状态查、按时间排"。

- 不为想象中的查询预建索引（每个索引拖慢写入）。
- ✅ 检查点：每个查询路径 `EXPLAIN` 过，没有全表扫描。

## 步骤 4：确定并发控制方式

对每个"读-改-写"路径选择：

1. 能用原子更新的用原子更新（`UPDATE ... SET n = n + 1`、条件更新 `WHERE status='pending'`）；
2. 否则默认乐观锁（`version` 列 + `WHERE version=?`）；
3. 争抢激烈才用 `SELECT ... FOR UPDATE`。

跨多行/多表的不变量用事务包裹，事务内不做网络调用。

## 步骤 5：写迁移（不停机安全）

- 迁移只前进，回滚靠新的前进迁移。
- 加列必须可空或带默认值；删列/改列名走三步：代码停用旧列 → 发布 → 下个迁移再删，禁止一步到位。
- 大表建索引用 `CREATE INDEX CONCURRENTLY`（PG）或在线 DDL。
- 数据回填与 schema 变更分成两个迁移，回填分批（每批几千行）避免长事务。
- ✅ 检查点：迁移在有数据的表上演练过，确认不锁表。

## 步骤 6：集成测试

用真实数据库（本地容器）验证：约束生效（违规插入被拒）、查询走索引、迁移可在旧数据上执行。

## 完成检查

- [ ] 每个查询场景有索引且 EXPLAIN 验证
- [ ] 约束落在数据库层并有测试证明生效
- [ ] 迁移演练通过、可不停机执行
- [ ] 并发路径有明确的控制方式与针对性测试

## 最佳实践（推荐，非强制；偏离时说明理由）

- 主键选型权衡：需要分布式生成或防遍历用 UUIDv7（保留时间局部性，别用 v4——随机分布打碎索引）；纯内部单库表自增更省。
- 深翻页用 keyset 分页（`WHERE (created_at, id) < (?, ?)`），OFFSET 在深页会全量扫过跳过的行。
- 高频写入的热点表上外键有锁竞争代价，可评估后省略并用应用层 + 定期一致性巡检兜底——但这是例外，默认仍加 FK。
- 高频计数/聚合不实时算：计数列原子自增，或预聚合表/物化视图定期刷新，接受秒级延迟。
- JSONB 字段确需查询时用 GIN 索引，但出现这种需求通常说明该字段应提升为列。
- 连接池大小从小起步（≈ 2×CPU 核数量级），压测定容——池子过大只是把排队从应用挪进数据库并加剧锁竞争。
- 大表（预期千万行以上）从建表起就想好归档/分区策略，事后拆远比事前贵。
